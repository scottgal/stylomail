# Giving StyloMail a Face: an Avalonia Console, a Management API, and a Local Decision Model Beside Jev

<!-- category -- AI,Architecture,Avalonia,StyloMail,.NET,Ollama,Decision Models,Patterns -->
<datetime class="hidden">2026-09-30T22:00</datetime>

**Draft held for screenshots and client testing.**

In the [last piece](/blog/stylomail-behavioural-inference-with-jev) I built up the inference side of StyloMail: a small set of typed semantic questions, some ordinary code that counts and compares, and explicit policy deciding what any of it justifies. What it did not have was a surface. There was no way for a person to look at a decision, agree or disagree with it, or change anything about the sender it concerned.

So this one is about giving it a face, and about a second answer to the question the inference side depends on. The brief was to make the **Avalonia console** and the **REST management API** work, and to add **Ollama's local decision models** as an option beside Jev rather than a replacement for it. To be plain about the motivation: the decision-shaped questions StyloMail asks are the same shape as the ones you meet in ticket triage, model routing and content moderation. Being able to ask them of a model running on the machine in front of you is worth finding out about.

> How much of the operational surface can be built as a client of an API that is correct on its own terms, and can the judgement under it come from a model you host yourself?

That is the experiment.

**StyloMail is research material for me to experiment with.** It is not a product and it is not in production. I am building enough of the idea to run it, change it and find out whether it is worth pursuing.

## "Working" has three states, and I keep needing to say which one I mean

There is **designed**, which is a document. There is **built**, which is code in the tree that compiles and has a route or a control. And there is **proven**, which is a measurement taken against the built thing that anybody could repeat.

Most of the confusion in a project like this lives between the second and third. A route exists and no client calls it. A control renders and no write lands. A suite passes and proves nothing, because the assertion was a substring that matched for the wrong reason.

I mention it up front because the rest of this piece is organised by that distinction, and because I would rather say "built, not proven" than round up.

A worked instance, because the distinction sounds abstract until it is not. The console has a block that lists failed readiness checks. For a while it rendered as a heading with nothing underneath it, and the model underneath was entirely correct. The property that reveals the block was raised; the property the list inside it binds to was never raised, so the window kept the empty list it had read before the first answer arrived. Two tests asserting the list's contents passed throughout, and they were right to pass. What found it was a rendered image of the window. That is the gap between a value being correct and a value being announced, and it is the best argument I have for rendering the thing you are about to claim.

## The console is an API client and nothing else

The decision the rest of the design follows from is in the project file, in a comment, before any code: the console has **no project references at all**. It does not reference the Host, and it does not reference Core.

That is deliberate and it costs something. Referencing the Host would let the two agree at build time and disagree at runtime, which is the failure this is meant to catch. Worse, the contract tests would be the Host tested against itself. So the wire contracts are **mirrored by hand**: enums, request and response types, field for field, against fixtures transcribed from the Host's own contract types. The intent is written in the fixtures: if the Host renames a field or an enum member, they should fail here, in a test named after the contract, rather than at runtime in front of an operator. Drift is expected to be loud.

Two consequences of that choice are worth writing down.

**An unknown enum member fails loudly.** StyloMail's `MailAction` has `Allow` as its zero value. In most code that is unremarkable. In a console whose job is to tell a person what happened to a message, quietly falling back to the zero member means a decision you did not understand renders as the most permissive action in the system. That is a fail-open in a safety surface. An unrecognised value in a decision-rendering path is an error, never a default.

**A missing key sends no request at all.** The client distinguishes four different failures: no key configured, the Host refused, the Host was unreachable, and the response was unreadable. Collapsing those into "could not connect" is how you end up with a screen that blames the network for a missing setting. One of them found that bug in itself: the readiness route is unauthenticated by necessity, and therefore carries no sensitive content at all, so it answered cheerfully while every authenticated call failed, and the first version of the window reported the wrong one.

**Evidence is not deleted to tidy a display.** The decision pane renders the evidence rows the Host sends, and one evening it met a response carrying the same signal id twice, one row per trend window. The pane was assembling a lookup keyed on the signal id, which throws on a duplicate key, and the whole pane went down. Every unit test passed, because every fixture had unique ids. The fix keeps both rows, and the comment in the code says why: dropping one would be the console editing the Host's answer. The better repair turned out to live on the other side. The Host now names the window as a field of its own on the row, so two rows in one scope can be told apart without anything having to disappear. That is the shape I want in a review surface: when the display and the data disagree, fix whichever of the two is wrong rather than deleting evidence.

The same instinct shows in smaller places. The mapping from an unreadable live-feed notice to a behaviour used to be a switch inside the window, where no test could reach it. It now lives in a type of its own, and the result it returns carries no kind, no id and no state, so a caller holding one has nothing it could wrongly render.

## The API's shape: the tenant comes from the principal

The management surface scopes everything to the tenant in the caller's principal. The listings take no tenant parameter at all, and the code says so in as many words: a cross-tenant read is not forbidden, it is **not expressible**, because there is no parameter to refuse and so nothing for a caller to name. The one place a tenant identifier does appear, in an assessment request body, is checked against the principal and rejected on mismatch rather than trusted.

That is a stronger property than it sounds. A check that refuses something has to be written correctly every time, and it has to be tested from both sides. A route that cannot name another tenant has one fewer way to be wrong, and the tests get to be about behaviour instead of about guarding a missing check.

Two other decisions in the route table are worth a sentence each.

**One route accepts two privileges, and it needed its own policy to do it.** Reading a decision list and releasing a message from quarantine are different privileges, and reading is strictly weaker than releasing: anybody who may release is somebody who may look. The route that serves both had to accept either, and the obvious way to write that in ASP.NET Core is `RequireAuthorization("a", "b")`, which is an **AND**, so it grants access only to the caller who holds both, and locks out exactly the user the route exists to serve. The union needed a policy with a name of its own. It is the only route in the table that accepts two privileges, and there is a comment above it saying why.

**The list refuses an unknown state by name.** The Host answers a request for `state=queued` with an explicit refusal rather than an empty list, because a queue state that does not exist and a query that is wrong are different things and the caller should be able to tell them apart. The console treats its list of states as a closed set to match, and the sidebar destinations were removed rather than left showing nothing. A dashboard should not invent columns either: a queued message carries a queue id, a state, an attempt count and recipients. It has no subject and no sender, so the screen does not show one.

## The empty list was not a bug

The first time the console listed messages against a running Host, the list was empty, and the honest thing to check first was whether the listing was wrong.

It was not. With no semantic provider configured, the Host builds an assessor that returns **Unavailable** for every message instead of assessing it, so nothing is ever classified, so nothing is ever queued, so there is nothing to list. The causal chain runs from the credential state, not from the query.

The distinction underneath it is the one I keep coming back to. **No provider and an unreachable provider are different states**, and the system treats them differently. A deployment with no provider queues nothing. A deployment whose provider is unreachable still records a decision, with every semantic dimension marked Unavailable and the reason recorded. What policy makes of that record is the part that moved while this piece was being written, and I am not going to describe it as settled: an all-unavailable message now computes to an allow at 7.7 over 15.0, which is 0.513, where it was held at a zero index before, and the ruling on that fail-open closes it by requiring an allow's semantic backbone to be either measured or not askable, with askability read from configuration rather than from whether the provider answered. Unknown is not zero, and an outage is not a verdict, and that is the line the tree now holds rather than the one it was being returned to. The ruling landed at `acb09f8`: a low index is refused on the allow path whenever a semantic dimension was asked and did not answer, recorded as `policy.allow_without_a_semantic_answer`, with askability read from configuration rather than from the provider's silence, on the reasoning that the only deployment able to reach a decision without semantic answers is one with a configured provider in a runtime outage, since a host with no semantic layer produces no assessment to decide on at all. The gate reads "asked and unanswered" rather than "not answered", so a dimension a message could not be asked about stays a fact about the deployment's shape rather than an outage of its provider.

That second case is also what makes a good test possible. The console's end-to-end harness seeds a decision by posting an assessment against a Host whose semantic provider is deliberately unreachable. The decision that comes back is a real one, produced by the real Host over the real route, and the pane's rule that an unmeasured dimension reads "not measured" rather than `0.00` is asserted over data that nothing wrote for the test. You can prove quite a lot without holding a credential, as long as you are honest about which state you are in.

## Built and unreachable is a state worth naming

Two things exist in the Host that nothing calls.

There is a SignalR hub for live traffic, mapped conditionally and refusing with a 404 on a deployment that has not enabled it, which is the right answer: "there is no feed here" and "you are not connected" are different sentences and a console that renders them the same way is lying about one of them. And there is a session route for a browser client that does not exist yet.

I do not think either is a defect. It is what a surface looks like while it is being built outward from the API, and the alternative, not writing the route until a caller exists, is how you discover that the route you needed was never quite the one you would have written. But it does belong in the article rather than in a list of features, because counting them as progress would be exactly the rounding-up I said I would avoid.

## The second decision model

The semantic side of StyloMail sits behind one port. A provider has to answer twelve bounded questions about a message and return, for each, a structured judgement in one of three shapes: a yes or no, a choice from a closed set, or one of a small number of ordered levels. The hosted Jev adapter was the only implementation of it. As of this stretch there are two, because the local one landed as a real adapter rather than a sketch, and I measured the model before it was written rather than after. The point of the exercise was that a model running locally can implement the same port. It now does.

I measured this against Ollama on this machine rather than reasoning about it. The instrument is a script kept beside the code, so the numbers have a reproduction rather than a story.

What I did not check at first was whether the prompt that instrument sent was the prompt the adapter sends. It was not, and that is the most useful error in this piece.

The probe rendered the message as a delimited bare body. The adapter renders the message **state** as JSON inside a single field, because the state is the thing the questions are asked about. That is not a cosmetic difference, and I found out by replaying a request the adapter had actually made, verbatim, against the same model and the same question set. The bare body gave one answer and the structured state gave another: **three of eleven dimensions flipped**, purely on how the message was wrapped. Eleven and not twelve, because the twelfth question is only asked when there is conversation context to ask it of, and this message carried none.

The tell, in the end, is the token count. The adapter's captured request is **1159 prompt tokens**. The bare-body variant is 855. The survey's own shape is 795. Three shapes, three numbers, and only one of them is the deployment.

So the figures that instrument gave me describe a prompt the adapter does not send, and I am not going to publish them as its behaviour. A prompt-shape result names the shape it was measured on, the same way a rate names the corpus that produced it. The instrument is being corrected or relabelled, and the number I intend to put here once it is, is one taken from a run through the Host rather than from a survey of the model on its own.

There is a second field the same rule applies to, one step further out. The classifier's input is four things: the message, the question set, tagged context and a behavioural profile. The shipping Host supplies all four, and the profile is not decoration, because Core puts it into the semantic cache key beside the words. The survey and the live tests supply two, so **every classifier-level figure in this piece was taken with no profile at all**. That is not a harmless omission: Core keeps "no profile supplied" and "a profile that says we looked and found nothing" as different inputs and gives them different cache keys, and a test asserts the two cannot collide, which is only worth asserting because the classifier reads the field rather than ignoring it. The consequence is a rule, and it is the same one as the prompt shape, and it is not particular to the profile: **a classifier-level number describes the provider under the state fields that were supplied**, and the profile is one of them. The authentication block is another, and it is the larger of the two. The trusted verification results reach the provider state with the verifier's own identifier among them, and only results from a trusted verifier are surfaced at all, because a result a message asserted about itself would let a sender certify its own authenticity; the Host then records whatever the caller sent, its verifier identifier included. All eight committed arms of the reply-in-thread measurement carry a trusted block: a connecting IP from the documentation range and an SPF pass from a named verifier. The classifier-level harnesses in this piece carry an authentication context with no results in it and its provenance flag set to incomplete, which is the same field saying that nothing verified the message. Nor is the block decoration, though how much it does is contested between two constructions of the same fixture, and I am not going to pick a winner between them. Varying it alone on one of them moved the answer, **B with a trusted block against A without one** at the three-turn window, with the one-turn window reading B either way, four cells at one call each (`site-provenance.json`). Varying it on the other moved nothing: the same two bodies, twelve questions, four conditions, three repeats each and interleaved, separated identically with a trusted block and without one (`axis-provenance.json`). The two agree where provenance is absent and differ where it is present, and there is no single field that decides it. Against the Host's own captured input, with the anchor checked against the served digest inside the same run, four distinct single-field changes each tipped the answer the same way on their own: the envelope sender to the thread participant, the envelope recipient the same, both envelope fields at once, and the authentication block removed. So the Host's exact input sits on a boundary rather than on a site, and the split is over-determined, which means a search that stopped at the first flip would have named whichever field it happened to vary first and been wrong about the other three (`site-envelope.json`, anchor and served digest both `b919a474...`, a baseline of B and five cells at one call each). The baseline has since been repeated rather than left at one call: five calls on that same input identity at that same anchor digest, B five times out of five with the five per-call digests identical and the run recorded stable (`site-close.json`, `section_1_repeats` 5, `section_1_stable` true). That repeat covers the baseline and not the spread, since the five variant cells remain one call each, and the same run separates what reaches the state from what decides it, because swapping the caller's verifier label moved the digest and left the answer at B either way, its own `section_2_verdict` recording that the string reached the state and the answer did not follow it. The block is the one field confirmed on two objects, this cell and the provenance cell above. What is not in doubt is that the block reaches the state at all, and that a classifier-level number here names its authentication provenance as well as its profile: the figures taken on this piece's own probe shapes are figures taken under incomplete provenance.

What survives is the reasoning, and the shape of the numbers, with the shape they were measured on named rather than implied. Answering twelve bounded questions with a model on this machine takes seconds per question and tens of seconds for the set, on CPU only: the per-dimension calls ran at medians of 1.487, 2.55 and 2.307 seconds, and one request answering every dimension for a single case took 9.373, 20.127 and 23.622 seconds. The first of those three arms asked eleven of the twelve dimensions and the later two asked all twelve, so the arms are not asking the same set, the medians are not a trend across them, and the difference between any two of them is not the price of the twelfth question. Two of those three medians were wrong in an earlier draft of this piece, taken from a value somewhere in the list rather than the middle of it, which is the same error as reading a declared window and calling it the applied one. Those are the survey's prompt and not the adapter's, and they were taken with no behavioural profile in the input where the Host always sends one, so they are not this deployment's timings on either count. The direction is still safe, for a reason that can be stated rather than trusted: the prompt-dependent term grows with the prompt, measured from 0.605 seconds to 14.563 seconds across the arms, so a prompt roughly 46% larger cannot be faster. Those comparisons are within one run, and the record is explicit about what it does not carry: the artifact names the endpoint, the model and the time it was taken (`measured_at` `2026-09-30T20:18:13+0100`), and it does not name the load on the machine while the arms ran (`nimble-survey.json`), so the arms can be set against each other and not against a timing taken somewhere else.

The comparison between the two askings is the part worth keeping, and it is easy to state wrongly. One dimension against all of them is a factor of roughly six to ten, which is not the comparison at all. Summing the per-dimension calls and putting that against the single all-dimensions call gives 17.0 against 9.4, 30.6 against 20.1, and 130.8 against 23.6, so the two land within one order of magnitude of each other and choosing between them is about failure isolation and prompt size rather than throughput. The caveat that belongs beside it is the one I would have missed: the worst of those ratios is a single stalled call measuring 103 seconds against a per-call budget of 120, so the fan-out shape multiplies a near-timeout tail by the number of dimensions. A reader told only "within an order of magnitude" does not see that, and it is a risk that lives in the shape rather than in the model.

The load story is two facts and I had it as one. The penalty on the first call is the model load and is not about the prompt, and the evidence for that is a single arm measured twice: the same question set carried a load of four milliseconds on one run and forty-two seconds on another, because in the first the model was already resident. When a load actually happens it ran from about four seconds to forty-two, and four milliseconds is what it looks like when there is no load to do. Separately, the prompt carries its own cost, measured between 0.6 and 14.6 seconds, and it grows with the prompt. Nothing in any of these runs reached a minute.

What I am not going to claim is that this is fast enough for a queue drain, and cutting it is the honest half of the check rather than modesty. Whether it drains a queue is a statement about how many assessments run at once and how deep the queue is, not a property of these numbers, and I do not have those two figures. The half that is measured is the other one: it is nowhere near fast enough for anything a person waits on, at seconds per question, tens of seconds for a full set, and a tail past a hundred seconds on a single call.

The measurement work is what the adapter was built from, and building it forced a decision that is not about the model at all: **what a deployment must be configured with before it can start.** The hosted provider holds a credential and refuses to run without one. The local one has no credential to hold, so its absence is the normal shape rather than a fault. An operator who selects the local model and is then told a provider key is missing would be told to fix something that does not exist, and an operator who selects the hosted model and finds no key required would be running half-configured while every surface said healthy. So the choice is a closed set with a name in configuration, rather than something inferred from whichever secret happens to be set in the process.

Two smaller rulings inside it are worth more than they look. The default is the hosted provider, because a default that moved existing deployments to a provider they never selected would change where their mail goes without telling them. And a name that matches nothing is a refusal rather than a fallback, because a host that quietly fell back to the hosted provider would send a deployment's mail to a third party while its operator believed the local model was reading it. Configuration that appears to work and does nothing is worse than configuration that is absent.

The smallest decision is my favourite one in the whole stretch. The name is matched against the provider names only, rather than parsed, because a numeric string would otherwise select the second member of the enum: someone types a `1`, and the deployment is running the local model because they typed a digit. A provider is named, not numbered.

One limitation belongs here rather than in the not-proven list, because it is a property of the model and not a gap in the work. **This provider's answer is narrower than the port can express.** It answers with a decision, so a dimension comes back as one of two values and a genuinely balanced result near the middle cannot be expressed at all. The code records that as a real limitation and refuses to smooth it with a mapping that would invent a gradation. That matters more than it sounds, and the next section but one is why.

## Chat is where local stops being a preference

The README is explicit that sending message content to a hosted classifier is a privacy decision rather than a configuration default, and it lists it under the things that **require an operator decision before enabling**. Tenants that prohibit it, it says, use the local evidence path with an explicit semantic-unavailable state.

That state is not hypothetical. It is live on the chat surface today, and it is the most honest thing in the system. `ChatAssessor` records **all twelve dimensions as unavailable** for every chat message, with a reason that says this deployment assesses chat locally, so no semantic evidence was obtained, and that the decision is an uninformed one rather than a confident one. The model version is left null, because as the code puts it, reporting an identifier would name a model that never saw this message.

The detail I would keep if I kept nothing else: no value is recorded for those dimensions, and the comment says why. A zero would read as a measured, calm answer. The code calls that the fabrication the availability model exists to prevent.

Which is why the brief for this piece named ticket triage and content moderation rather than mail. Internal conversation is a larger privacy step than inbound mail, and a model on your own machine is the one way to give that surface semantics without taking the decision the README says an operator has to take. That is a better argument for a local decision model than any latency number in this article.

What I am not going to claim is that it is done, or that the swap is mechanical. The port's input is mail-shaped today: it requires a mail analysis input, and the chat assessor does not call the port at all. Whether a short conversational turn with no headers and no subject can be expressed as that input is a real question about how local the local option is, and nobody has measured a local model against chat-shaped text. I would rather leave that visible than round it up.

## Two Ollama servers, and a version that reports something else

The trap in this lane cost real time and is worth writing down.

There were **two Ollama servers on the machine, and the default port was the wrong one.** The app bundle was serving on the standard `11434`, and a Homebrew install was serving on `11435`. They were different versions, and only one of them could run the model.

Worse, `ollama --version` printed the version of the **server it reached**, not of the binary it was invoked as. Calling the new binary directly still reported the old number, because it was asking the old server. So the same command gives different answers depending on which server happens to be up, and the command looks like it is describing the tool.

There is a smaller version of the same lesson inside it, and it is the one that caught me. Ollama's `/api/show` for a model succeeds even on the server that cannot serve it. "The model is there" is not evidence that the server can run it.

And the context window is three different numbers depending on where you read it. `/api/show` reports the model's maximum as 262144. The model's build parameters carry a `num_ctx` of 8194, which is a default it was built with and not a window it is ever given. What the server actually applied to a request is neither of those: a request for 8192 was cut between **4098 and 4104 tokens**, a band a few tokens wide rather than an exact boundary, and requests for 4096 and 16384 were cut at 2050 and 8194. A control showed the count is a real cut rather than a fraction of the prompt, because a fixed 3,720-character prompt evaluated to the same **824** tokens under a requested 2048 and under a requested 8192. So the rule is a relationship rather than a constant, and the adapter derives the applied window as **half** the requested one, deliberately at or below the floor of that band, because the value feeds a truncation backstop: a bound that fires a few tokens early costs an answer on a message that was almost certainly cut anyway, and a bound a few tokens late would let a partly-read message through as a complete one.

I had this wrong in an earlier draft of this piece. I took 8194 from the build parameters and wrote it as the window the model loads with, in a paragraph whose entire point is that you find these numbers by measuring and never by reading. That makes it the best example in the piece rather than an exception to it: reading the parameter gave a plausible number, measurement contradicted it, and the number I should have quoted was the one nobody had written down.

The consequence for the design is concrete: an adapter whose default endpoint is Ollama's default endpoint is pointed at the wrong server on a machine like this one, and the version it reports will be the server's, so it will agree with itself while being wrong. That has to be configuration, and the server's version belongs in the report.

## Count what came back against what was asked

The most useful bug in this whole piece was in a measuring instrument, not in the system.

A parsing script read the twelve dimensions out of the source with a regular expression, and the expression ended in a pattern that matched the separator between entries. The last entry in the array does not end that way. So the first run measured **eleven dimensions out of twelve** and reported nothing unusual. A silent drop looks exactly like a clean run.

The same expression is still sitting in an earlier harness, in a spike that compared a different local candidate model against hosted Jev. Which means the number that spike reported for conversational continuity **does not exist**, and nothing in its output said so. The newer harness does not have the bug because it reads the dimensions differently; the older one still carries the expression, which is the honest state of it. The second bug the same review found was the same species: one of the dimensions declares its identifier as a bare constant rather than a string literal, so a reader that only understood literals dropped it too.

The rule this lane keeps re-learning is one sentence long, and it applies far past parsers. **Count what came back against what was asked.** A number with no reproduction is not a measurement. This is the stronger version: a number with a reproduction is not a measurement either, if the instrument is quietly dropping one of the things you asked about.

There is a version of this that is not about parsers at all, and it turned up while I was checking a number in this piece rather than while I was writing it. `dotnet test` prints its summary line, `Failed: 0, Passed: N`, for however many tests finished. Only after that does it print `Test Run Aborted.` if the test host process died. So a suite that crashed partway through still reports a clean zero failures. The Host suite does exactly that today: an unhandled exception on a queue worker's drain timer takes the whole process down from a thread-pool thread, its owner measured three full runs aborting at three different points, and my own run aborted the same way, with a `Failed: 0` style summary sitting above the crash. It is not that the suite is broken, it is that it is unreliable in a particular direction: it aborts about half the time and completes the rest, and a reader with only the summary line cannot tell which kind of run they are holding. That is the same failure as the regex wearing different clothes, and it is worse, because a build server reads the summary line and believes it. The check is the same check. Count what came back against what was asked, and when the two disagree, believe the count of things you asked for.

## What is not proven

I would rather be specific about this than end on a summary.

**The local provider is landed, and landed is not proven.** It is a second implementation of the port, selectable by name, with its own suite and its own containment tests. What I have not done is quote a console count from a deployment running it. The counts below come from runs against a deployment with no working provider at all, and carrying them across to a different deployment because both are "done" is exactly the rounding-up this section exists to prevent.

**History cannot buy a quarantine today.** Two dimensions the adaptive layer produces, the campaign grouping and the behavioural deviation, are not keys in the dimension weights, so those rows are counted in neither the numerator nor the denominator of the composite index. Eight near-duplicate messages from one sender held the index at 0.589041 to fifteen decimal places, in the one case where the campaign row is absent and in the seven where it is present. That was measured through the Host route, which supplies no conversation context, so the continuity dimension whose arithmetic changed in this stretch is not in play in that number. It has since been measured with a window supplied, and the reading that came back is the next bullet rather than a new number here, because the row it produces is now out of the index in both directions. The route that crosses the quarantine threshold is vehemence in one message, not accumulation across many, and the accumulation machinery that exists is not yet wired into the arithmetic that authorises anything.

**The continuity question does not discriminate, and the index no longer counts it.** I held one message fixed and moved only the window around it, varying the window's content and its size, at two turns and at three: forty calls through the shipping adapter against the local model, ten per cell, one warmup, and the answer was **B in every one of the forty**, one distinct whole answer vector across the four cells, no unavailable runs, with prompt tokens of 1249, 1227, 1294 and 1255 and each three-turn cell strictly larger than its two-turn partner, so the window was sent and its size reached the model. That is the artifact `continuity-cells.json` for the cells, taken under a requested window of 8192 and an applied one of 4096, from a run whose own console log beside it, `continuity-cells.log`, records one test, `Failed: 0`, `EXIT=0` and a duration of thirteen minutes and twenty-nine seconds. The test asserts only that the question was asked and that every answer is a legal code. The B in every cell is what was **reported**, not what was asserted, and the gap between those two is why this section exists.

What it does not establish is that the model is right or wrong, and the reason is arithmetic rather than modesty. Forty runs with no A cannot separate "the window advances the state, so B is the correct answer" from "the question is biased to B by the shape it is asked in", and the first of those has since been given a name. The axis the evidence points at is **containment**: whether the message's own content is already in the window beside it, which is a question about the message and the window rather than a question about risk. This test held the message fixed, so every one of its cells shares whatever containment status that message has, and no cell of it can tell containment apart from the shape the question was asked in. The limit is in the design rather than in the run, and it is the limit I would want a reader to take from it. The competing explanation is live in this repository rather than hypothetical: the same case answers B when the adapter's own captured request is replayed verbatim and A when the message is rendered differently, three runs each way, in `replay-divergence.json`. ## A probabilistic negative does not authorise

The most interesting thing built in this stretch is a refusal, and it is a policy change rather than a model change.

Below the threshold that would hold a message, delivery is now authorised only when at least one available **deterministic** signal was measured beside the risk index. The reason is specific. A model's false negative is indistinguishable from its true negative. It does not arrive as a missing row; it arrives as an available row with a value of zero, which **raises** the fraction of expected evidence that is present rather than lowering it, and so can satisfy both of the coverage guards the index is checked against. A model's silence could walk a message to delivery and the guards would report a thorough assessment.

That is not a theory about what a model might do. A live test put an instruction inside the body of a message, ordering the real local model to answer the same letter to every question, and it **flipped three of eleven** dimensions on the credential-request fixture. That test is a live fact, and the shape of that matters for reproducing it: it probes for a model server and skips when none answers rather than failing, so it reports nothing at all on a machine with no model installed, and it is not opt-in either, because the endpoint it probes is the provider's own default, so on a machine holding the model it runs as the suite's normal state rather than on an arrangement. The figure above needs the server rather than the suite. Eleven rather than twelve, because one dimension cannot be asked without conversation context and is reported as not applicable and masked, never scored low. That number carries the qualifier from earlier in this piece as well: the test drives the classifier directly rather than through the Host, so no behavioural profile was in its input, and it is a fact about the model under that shape rather than about the product. Against the shipped thresholds a third of the dimension weight answered entirely zero already licenses an allow, so an attacker needs only to keep the index under the hold line. The test is careful about what it establishes and I want to keep its framing: it is a recording rather than a guard, and its assertion is containment. The answer that came back was a legal code for every question asked. Whether it was **true** is not something the adapter's structure can promise, because an attacker writes text this model reads. Reading a flip is a real finding. Reading none would not have been proof of immunity, and the comment in the test says so.

The line worth keeping is this: **a probabilistic negative does not authorise, it only fails to forbid.** The reason code left behind says as much, and it names the provider the allow was resting on.

There is a companion ruling about where evidence comes from. Evidence origin has four values, and corroboration is deterministic origin **together with** an available row rather than a label on its own, and a test pins the second half: `A_deterministic_row_that_is_unavailable_does_not_corroborate`, added at `3e97936`, whose own remark records that the label stays sound only by facts that live outside policy rather than by anything the gate guarantees. Deterministic names where a row comes from rather than what it was read from, and there is a row that shows the gap: the unavailable behavioural-context marker carries deterministic origin and an unavailable value, because what it reports is the sender's profile store rather than the message, so a filter on origin would keep it (`Origin = EvidenceOrigin.Deterministic` with `Availability = Unavailable` on `AssessmentEvidenceIds.BehaviouralContextUnavailable`, `src/StyloMail.Assessment/MailAssessor.cs` at `c742fcc`), while the enum carries an origin for evidence derived from profile comparison and temporal behaviour, `EvidenceOrigin.Behavioural`, and this row does not use it. Behavioural evidence is admissible and explicitly **not** corroboration, because it is learned, and an attacker shapes the traffic that produces it. There is a test whose name is the ruling: behavioural evidence alone does not corroborate an allow.

And then the honest part, which is filed rather than smoothed over. The gate requires that checkable evidence was *measured*, not that it *agrees*, and those are not the same claim. The deterministic findings were unweighted at the commit this piece was written against, so a displayed-link mismatch at full confidence could not raise the index, and a benign deterministic row sitting beside it was enough to satisfy the gate. That sentence was true of the tree then and false of the tree now, and the honest form is all of it: the gap was measured, filed and pinned by a test whose name carries the correction, `A_concerning_deterministic_finding_now_enters_the_denominator_and_holds`, renamed from `A_concerning_unweighted_deterministic_finding_does_not_yet_block_an_allow`, whose old name survives in the comment beside it, and the repair is landed rather than ruled, committed at `acb09f8`. Ten risk-shaped deterministic signals gain weights with declared units, ratios and booleans as they are and counts through a bounded step, while no byte total and no digest is ever weighted and thirteen signals stay out of the arithmetic altogether. What that buys and what it does not is the part the polarity invites a reader to get wrong: a finding that **enters the index** is not a finding that **blocks**. A link mismatch at a weight of 1.0 beside a semantic backbone answered calm gives 1.0 over 8.3, which is 0.120, against a hold threshold of 0.55, so one checkable finding on its own would need a weight of 8.9 to cross it, and blocking power is not being given to the weighted index at all: a checkable fact that must refuse belongs in tier 2 of the precedence order, the verified security rules, where it does not dilute a weighted mean. That tier is a named three in the landed code rather than a principle: a trusted authentication failure, an IDN homograph and an attachment type mismatch refuse, and the other seven stay index-only because their false positives are structural rather than rare, which is the same judgement as the one above arriving from the other side. A refusal rule that holds a large share of ordinary mail is not a stricter system, it is a system nobody can run. So what closes here is the gap's mechanism, and its headline is re-scoped rather than closed, by design rather than by omission. The alternative that would have done it without units, a threshold guard, is refused by measurement rather than by taste, because a rule that held anything above a threshold would hold every message with a stored attachment. The system is honest about the shape it is in, and that is more interesting than a clean success would have been.

The last ruling in this stretch is the one I would keep above all of them, and it came from a measurement rather than a review. **A response should carry the inputs to its own arithmetic.** Two very different things currently render identically in the decision view: a dimension that was counted and scored zero, and a dimension that was deliberately excluded from the arithmetic. Both arrive as an available row valued at zero, and neither carries its weight or the denominator it was divided by. That is the shape the Host served at the commit this piece was written against, and the repair has landed and been committed since, at `6f8b077`: publish the weight and a counted flag per row, and the denominator beside the index. So a reader who recomputes the index from the rows they were served gets the pre-change answer and has no way to know they were working from an incomplete sentence, and the fix is a change to what the Host serves rather than to what it decides. It belongs in this piece because it is the same rule as everything above, arriving from the other end: if a number cannot be checked from what you were given, you have not been given a measurement yet. It is also the reason the exclusion I described earlier matters twice over, since masking a row changes the denominator, which is exactly why the denominator has to be visible.

The ruling on how those fields arrive is the part I find most interesting, because it is a decision about honesty rather than about schema. The three members become nullable but stay required, and a null means exactly one thing: the build that made this decision did not record it. No sentinel value stands in for the gap, and the weight is not reconstructed from today's configuration, because a decision whose arithmetic is rebuilt from a later build reconciles, and reconciles falsely, which is worse than one that admits it cannot be checked. A row written before the arithmetic existed therefore loads with nulls and says so, rather than loading with numbers that add up for the wrong reason.

## What a corpus can and cannot settle

The next piece of work is the one that decides whether any of this is worth continuing: a full harness for the desktop client, and a generator of spam and benign mail to point at it. The harness is design rather than result, so what follows is design. The datasets that will supply the mail are already measured, and between them they make the rules concrete.

Two rules go in before a single number comes out, because a corpus is the easiest place in a project like this to fool yourself.

**A rate from a corpus is quoted with the corpus named, and never as accuracy.** "It caught most of the spam" is a statement about a pile of mail I wrote myself, on a machine, in an afternoon. It is worth knowing, and it is not the same claim as how the system performs on mail it did not grow up with.

**Every case carries a split between a fact that can be checked and a label that is only my judgement.** "This message asks for a credential" is checkable by code: the message either asks for one or it does not, and a reader can disagree with me and be shown the message. "This message is malicious" is not checkable by anything. Recognising it as my opinion rather than as evidence about the world is the difference between a corpus that measures something and a corpus that agrees with itself.

Both rules have a worked instance already, and neither is a hypothetical.

The first dataset is named like a spam and ham email corpus, and the file inside it is even called `email.csv`. It is not an email corpus. Its rows are short messages, just under six thousand of them, 747 labelled spam, with a mean body of about eighty characters. The mail headers that make an email an email are simply absent from every row, and a couple of dozen of the messages mention a link at all. So the one claim it cannot support is any email-shaped rate. That is not a complaint about the dataset, which is fine at what it is. It is the reason a rate always travels with its corpus named.

The second is a fifty thousand row synthetic phishing table that ships its own label and its own phishing probability as columns, along with sender reputation, domain age and SPF, DKIM and DMARC verdicts. Two things follow. Quoting its label as accuracy would be quoting its author's model back at itself, because the label is the outcome of a generation process rather than an observation of the world. And because the deterministic checks a real pipeline would compute are already sitting in the table as columns, a detection rate measured on it would be measuring that generator rather than anything I built. It is a denominator with a provenance, and the provenance is the point.

The exclusions belong in the write-up as much as the passes do, and one of mine turned out to be wrong, which is more useful to write down than a clean list. I had it that this harness cannot drive a message into the quarantined state. It can. On a Host whose provider was the local model, a ladder of messages crossed the quarantine threshold and the state was reached twice, with the release measured all the way back out. What a deployment with no working provider cannot do is populate the message list at all, because a deployment that queues nothing has nothing to list, and the click-through from a message to its decision is then missing a message rather than a route. The route exists and the console uses it. So the empty list was a fact about a deployment and not about the console, and I had carried it one step too far into a claim about the console's reach. An empty list and an unreachable state are different sentences, and so are a missing feature and a missing fixture.

There is one more rule the corpus work produced, and it is the best worked example of the first two that I have. The message that finally crossed the quarantine threshold was written while looking at the model's earlier answers. The fixture itself is legitimate: putting a system into a state is how you test what happens in that state. But it reaches its number partly by fitting the model's judgement, so it can never be a detection rate, and it is labelled in the manifest as exactly what it is, a threshold-targeted case. A rate produced by tuning against the model's own answers is a statement about the tuning. That is the first rule arriving from the other end, and it is the sharpest version of it I have: the number is real, and the sentence it can support is far smaller than it looks.

## Why the shape is worth keeping

The invariant from the first piece survives all of this. Probabilistic components produce evidence. Only deterministic policy authorises a side effect. The console is downstream of the policy, not a second place where decisions get made, which is why it can be rebuilt, replaced or thrown away without touching the thing being tested.

A local decision model does not change that either. It is a second implementation of the same port, answering the same question set in the same three shapes, and the interesting property is precisely that swapping it should change the answer and not the architecture. Same questions, same evidence, same policy, different model. What has changed is that the swap is now a runnable question rather than a design question: the adapter is built and selectable, so the sentence I want to be able to write is the one where a deployment reading its mail locally holds a message the hosted model would have let through, or does not. I cannot write that sentence yet, and I would rather leave this piece ending on the version of it that is true.
