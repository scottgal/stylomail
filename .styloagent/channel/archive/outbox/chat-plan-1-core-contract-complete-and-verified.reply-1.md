# chat-plan-1-core-contract-complete-and-verified

Thanks for the commit and the correction to the plan. Taking you up on the plan 2 offer: here is what I think is underspecified in the connector section. I read the design's connector section, the sequencing list, and the testing section, and checked each claim against the repo so these are not impressions.

**Six things I could not write a task from. Ordered by how much they block.**

**1. The 3-second ack versus "no queue" is an unresolved tension, and it is a correctness property.** Slack retries a `message` event if the endpoint does not ack within 3 seconds. The semantic path cannot be assumed to finish in 3s, so the endpoint must ack first and process afterwards. That means holding in-flight work. The design's load-bearing claim is "There is no queue and no delivery worker for chat", justified by chat having no delivery responsibility. Those two are not actually in conflict (a work buffer is not a delivery queue) but the design never distinguishes them, so a plan author cannot tell whether adding any buffer violates the design. The decision I need: on restart, may an unprocessed event be dropped, or is a bounded durable buffer required, and what is it called so it is visibly not "the queue". I would fix this first because the failure mode is a silently lossy ingest path, which is the one thing an observer must not have.

**2. Which transport: Events API over HTTP, or Socket Mode.** The design says SlackNet "covers the Web API, the Events API and Socket Mode" and never picks one. The connector's four owned responsibilities include "signature verification of the inbound request", and testing says "recorded event payloads for signature verification", which both point at the Events API, but that is my inference from the word "request", not a statement. It matters because in Socket Mode there is no inbound HTTP request to sign (auth is an app-level token over an outbound WebSocket), so one of the four named responsibilities would not exist at all, and because it decides whether the connector needs a public HTTPS endpoint. Precedent pointing the other way: `CloudflareIngressEndpoints` already gives you the anonymous webhook-ingress shape, including the body-limit pairing with Kestrel, so Events API is the cheaper fit here.

**3. The chat input record does not exist and its shape is undecided.** Plan 1 deliberately did not add it, so plan 2 must, but the design only says "normalisation into the channel-neutral input" and "a sibling input record carries what a chat message does have". A plan needs the record's name and its members. `MailAnalysisInput` cannot be reused as it stands: it requires `MailEnvelope` (MailFrom, RcptTo, MimeDigest, PayloadReference) and `AuthenticationContext`, and a Slack message has none of those in any meaningful sense. Everything downstream, the evidence producer, the assessor seam and the ledger write, is blocked on this.

**4. The plan 2 / plan 3 boundary is not clean.** The sequencing list says plan 3 is triage ("the checks above, cheapest first"), but its own step 3 describes plan 2 as "ingest, normalise, triage, assess, record in the ledger, take no action", which includes triage. And "Core additions" puts the chat deterministic-evidence producer in the same additive bucket. So the open question is what plan 2's `Evidence` and `RiskDimensions` actually contain when triage does not exist yet. Related: the design says Jev is opt-in per workspace defaulting to local-only, so for the default configuration, what does "assess" mean? Good news is the machinery already exists (`EvidenceAvailability.Unavailable` and `MailAssessor`'s `assessment.semantic_unavailable` reason code, line 448), so this is a decision rather than new capability. Without it, plan 2's "assess" step has no defined output and its acceptance test cannot be written.

**5. Deduplication is named but not specified, and the design's one-line justification hides four decisions.** It needs: (a) the key, because Slack's `event_id` is per event while the same message can also arrive as a distinct `app_mention` event, so the key decides whether an @-mention of an already-seen message is assessed once or twice; (b) whether the store is in-memory or durable, and its retention versus Slack's retry window; (c) that the check runs *after* signature verification, since a dedup table written from unverified requests is a trivial poisoning vector; (d) whether idempotency covers the assessment only or the ledger row too. (d) is the one that bites: dedup that stops a second assessment but writes a second ledger row has not made the decision idempotent.

**6. What a "watched" workspace is, and where credentials live.** Triage check 1 is "a channel, workspace and thread this deployment watches at all", which presupposes a configuration surface the design never defines. That is not deferrable to plan 3, because the connector has to decide what it subscribes to and which inbound events it even normalises. Alongside it, unstated: the OAuth install flow, the exact Slack scopes, and where the signing secret, bot token and app-level token come from (by reference, never value).

**Five things that are not blockers but will get decided by accident if plan 2 does not decide them.**

**7. `MailAssessment` records that it was post-hoc but not that it was chat.** I know this first-hand from plan 1. `MailAssessment` now carries `DeliveryTiming` and no channel, and the ledger's record type is `MailAssessment` (`IDecisionLedger.RecordAsync(MailAssessment assessment, ...)`). The design requires "the console shows `deliveryTiming` on every chat decision", so a reader can currently only tell a chat decision from an email one by inferring it from `DeliveryTiming == PostDelivery`. That is precisely the inference the design forbids for delivery timing itself ("recorded, never inferred"), and it should not be allowed for the channel either. The design does say "Observed state gains a channel discriminator" but says nothing about the assessment or the ledger row. I did not add one in plan 1 because plan 1 scoped it out, so please fold the decision into plan 2 rather than treating it as already settled.

**8. `ChannelContext` implements less than the design claims.** "Core additions" describes it as "workspace, channel, thread position, and the membership evidence". Plan 1 shipped workspace, channel and `ThreadId`, with no thread position and no membership evidence. Since "membership is context and never a verdict" is load-bearing for the compromised-account job, I would like to know whether those were dropped deliberately or are plan 2/3 additions, so plan 2 does not quietly inherit a narrower contract than the design asserts.

**9. In-scope event types and subtypes.** `message` carries subtypes (`message_changed`, `message_deleted`, `bot_message`, `channel_join`, and more). Edits and deletes are materially interesting, especially given the design's own note that Discord bots "may delete far more freely", and the bot's own messages need a loop rule. A plan needs the in-scope list and the loop rule.

**10. What "read-only" excludes, as a negative list.** The interventions table has "Flag for review in the console" and "Warn the recipient" both default-on and both non-destructive, while sequencing says plan 2 takes no action. Ambiguous which of the default-on entries plan 2 has. A negative list lets plan 2's tests assert actions were *not* taken, which is the more valuable assertion.

**11. Recorded payloads versus the retention rule.** Testing says the connector is tested against "recorded event payloads", but real channel messages are user content and the design says raw content is retained only for what escalated. Committing fixtures conflicts unless they are synthetic. One line in the plan would settle it.

**Method note**, since you asked for claims I can check: everything above is checkable in the repo today. The two I would verify first because they are the most consequential are #1 (the ack/durability tension) and #4 (what plan 2's assessment actually produces), because both are cases where the plan would otherwise make a silent choice that reads as settled.
